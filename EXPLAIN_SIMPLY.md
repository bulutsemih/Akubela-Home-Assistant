# Как это всё работает — простыми словами

Этот документ — не для программистов, а для тех, кто хочет понять
суть, не читая код. Если вы знаете, что такое HTTP-запрос или что
такое JSON — можно сразу перейти к разделу "Как это всё соединено".

## Задача одним предложением

Home Assistant (HA) и панель Akubela — это две независимые "умные"
системы, которые ничего не знают друг о друге. Наш бридж — программа-
переводчик, которая сидит между ними и постоянно слушает обе стороны:
как только что-то меняется в одной, тут же передаёт это в другую.

## Разбираемся с технологиями по одной

### HTTP: "письмо с ответом"

Это то, чем вы пользуетесь каждый день, открывая сайты в браузере.
Работает как обычная почта: вы отправляете запрос ("дай мне страницу
google.com"), сервер отвечает ("вот страница"), и на этом всё —
соединение закрывается. Если через секунду понадобится что-то ещё —
нужно отправлять новый запрос заново.

Для нашей задачи это плохо подходит: нам нужно **мгновенно** узнавать,
что кто-то нажал кнопку на панели, а не спрашивать "ну как там, ничего
не изменилось?" каждую секунду (это называется *polling*, и это и
медленно, и создаёт лишнюю нагрузку).

### WebSocket: "телефонный звонок, который не кладут трубку"

В отличие от HTTP, WebSocket — это **постоянно открытое** соединение.
Представьте не переписку письмами, а телефонный звонок: трубку взяли
один раз, и дальше обе стороны могут говорить в любой момент, не
перезванивая заново. Именно поэтому и HA, и Akubela используют
WebSocket — так события (нажали кнопку, изменилась температура) можно
доставить **мгновенно**, в момент, когда они произошли, а не когда
кто-то в следующий раз спросит.

Наш бридж держит **два таких "звонка" одновременно** — один к HA,
другой к Akubela — и слушает оба сразу, 24 часа в сутки, пока работает
`main.py`.

### API и "команды": как заставить что-то произойти

API (Application Programming Interface) — это просто список команд,
которые понимает система. У HA и у Akubela API устроены очень похоже
(это отдельная удача — подробнее ниже), команда выглядит примерно так:

```
"включи свет с именем light.kukhnya на 50% яркости"
```

В коде это называется `call_service` — "вызови сервис [функцию]
[домен: свет] [действие: включить] у [конкретного устройства] с
[такими-то параметрами]".

### JSON: язык, на котором все эти команды записаны

И HA, и Akubela передают данные в формате JSON — это просто текст,
структурированный как анкета из полей "имя: значение":

```json
{
  "тип": "включить_свет",
  "устройство": "light.kukhnya",
  "яркость": 50
}
```

Любое сообщение, которое летает между HA, бриджем и Akubela — это
JSON-текст. Ничего магического, просто общий "язык", понятный обеим
системам.

### MQTT: доска объявлений

MQTT — это третья технология, используется в одном конкретном месте
(родные датчики панели → HA). Работает как доска объявлений в подъезде:
кто-то **публикует** записку с темой "квартира 5, температура: 22°C"
(это называется *publish* в *topic*), а все, кому интересна именно эта
тема, **подписаны** (*subscribe*) и сразу видят новую записку. Писать и
читать не обязательно одновременно — записки просто лежат на доске,
пока их не заменят новыми.

Home Assistant умеет "читать" такую доску объявлений сам, без
дополнительного кода с нашей стороны — это и называется MQTT Discovery:
мы публикуем правильно оформленную записку, и HA сам создаёт нужную
сущность.

## Как это всё соединено

```
┌─────────────────┐         ┌──────────────┐         ┌──────────────────┐
│  Home Assistant  │◄──WS───┤    Бридж      ├───WS───►│  Панель Akubela   │
│  (ваши устройства│         │  (main.py)    │         │  (её устройства  │
│   и автоматизации)         │               │         │   и виджеты)     │
└─────────────────┘         └──────┬───────┘         └──────────────────┘
                                     │
                                     │ MQTT
                                     ▼
                            ┌──────────────┐
                            │ MQTT-брокер  │  (для родных датчиков панели)
                            └──────────────┘
```

Бридж — это один запущенный процесс (`python main.py`), внутри которого
работает сразу несколько независимых "потоков внимания" (в коде это
называется *корутины* / *asyncio tasks*) — один следит за изменениями в
HA, другой за изменениями на панели, третий раз в 5 минут сверяет
полный список устройств, и так далее. Все они работают одновременно, не
мешая друг другу.

## Пошаговый пример №1: включаете свет из Home Assistant

1. Вы нажимаете "включить" на карточке лампы в приложении HA.
2. HA обрабатывает нажатие и **сам** меняет состояние лампы у себя
   внутри — с "выключено" на "включено".
3. HA, раз состояние поменялось, **тут же** (без задержки, по тому
   самому открытому WebSocket-"звонку") сообщает об этом всем, кто
   подписан на события — а наш бридж подписан.
4. Кусок бриджа под названием `state_forwarder.py` получает это
   сообщение, смотрит: "о, это лампа, а она у меня есть на панели —
   вот там её код называется `light.abc123`" (эту связку он помнит из
   своей "записной книжки" — файла `bridge_state.json`).
5. `state_forwarder.py` шлёт панели свою команду по её собственному
   "телефону" (второй WebSocket): "включи `light.abc123`, яркость 80%".
6. Панель выполняет команду — виджет на экране загорается.

Всё это происходит за доли секунды.

## Пошаговый пример №2: нажимаете виджет прямо на панели

Работает симметрично, только в обратную сторону:

1. Вы нажимаете кнопку на экране панели.
2. Панель меняет своё внутреннее состояние и сообщает об этом всем
   подписчикам по своему WebSocket — а бридж подписан.
3. Кусок бриджа `control_bridge.py` получает сообщение, находит
   соответствующую сущность в HA через ту же "записную книжку".
4. Отправляет команду в HA по его WebSocket.
5. HA меняет состояние — карточка в приложении обновляется.

## Зачем бриджу "записная книжка" (`bridge_state.json`)

Панель и HA называют одно и то же устройство **по-разному**: в HA это
`light.kukhnya`, а на панели — какой-то случайный код вроде
`3ff0e2765d15439ba3ef902470b48c70`. Файл `bridge_state.json` — это
таблица соответствия "имя в HA ↔ код на панели", которую бридж ведёт
сам и сохраняет на диск, чтобы не забыть эту связку даже после
перезапуска.

## Что такое "петля" и почему это опасно

Представьте, что двое людей одновременно пытаются вежливо пропустить
друг друга в дверях — и оба раз за разом отступают назад одновременно.
Получается бесконечное "после вас — нет, после вас".

То же самое может случиться с бриджем: HA меняет состояние → бридж
передаёт это в Akubela → Akubela из-за этого меняет своё состояние → бридж
видит изменение и передаёт его обратно в HA → и так до бесконечности,
причём очень быстро (сотни раз в секунду), забивая канал связи.

В коде есть специальный "сторож" (`loop_guard.py`), который считает,
сколько раз подряд одно и то же устройство переключилось за короткое
время. Если слишком много — он временно "затыкает уши" именно для
этого устройства на минуту, чтобы дать петле остановиться, и громко
пишет об этом в лог.

## Мини-словарь

| Термин | Что это значит простыми словами |
|---|---|
| **API** | список команд, которые понимает система |
| **WebSocket (WS)** | постоянно открытое соединение для мгновенного обмена сообщениями в обе стороны |
| **HTTP** | классический запрос-ответ, как письмо по почте, соединение не держится открытым |
| **JSON** | текстовый формат для передачи данных в виде "поле: значение" |
| **MQTT** | доска объявлений: одни публикуют, другие подписываются на нужные темы |
| **call_service** | конкретная команда "сделай вот это с вот этим устройством" |
| **entity_id / device_id** | внутреннее имя-код, под которым система знает конкретное устройство |
| **state_changed** | событие "у устройства поменялось состояние", которое система рассылает подписчикам |
| **subscribe / подписка** | "сообщи мне, если что-то из этого списка произойдёт" |
| **идемпотентность** | свойство кода: если запустить его повторно с теми же данными, ничего не сломается и не задвоится |
| **loop_guard / петля** | защита от бесконечного зацикливания сигналов между двумя системами |
| **feature** (в контексте Akubela) | номер, который определяет, какой именно виджет (набор кнопок/слайдеров) увидит пользователь для устройства |
