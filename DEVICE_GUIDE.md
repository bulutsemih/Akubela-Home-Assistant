# Памятка: добавление устройств и калибровка виджетов

Практическое руководство "что делать, если...". Для понимания *почему*
это так устроено — см. [`ARCHITECTURE.md`](./ARCHITECTURE.md).

## Как HA-сущности превращаются в устройства Akubela

| HA домен | `device_type` Akubela | `feature` | Статус |
|---|---|---|---|
| `light` (on/off) | `Light` | `0` | подтверждено |
| `light` (brightness) | `Light` | `1` | подтверждено |
| `light` (color_temp) | `Light` | `4` | **откалибровано визуально**: `1`/`4`/`7` — слайдер, `4` даёт яркость+цвет вместе. Яркость передаётся как `brightness_pct` (0-100), НЕ `brightness` (0-255) |
| `switch`, `input_boolean` | `Switch` | `0` | подтверждено |
| `climate` | `Floor Heat` | `0`/`1` | режим подтверждён; температура — по аналогии |
| `cover` | `Cover` | `1` | **откалибровано визуально**: `1`/`4`/`7` — слайдер с позицией, `0`/`2` — кнопки без слежения за ходом, `3`/`5`/`9` — кнопки "по ширине", `6`/`8` — угол наклона (жалюзи) |
| `lock` | `Lock` | `0` | не откалибровано, сервисы `lock`/`unlock` по аналогии |
| `sensor` | — | — | ❌ **не работает**: панель не создаёт устройства категории `Sensor` через `device/add` вообще (подтверждено контрольным тестом с заведомо рабочим `device_type`). Держите `sensor` вне `PUSH_DOMAINS` |
| `scene` | (отдельный API `scene/add`) | — | подтверждено |

Логика — в `device_registry.py:build_device_spec()`.

### Как узнать `feature` для нового типа — сделали дважды, работает надёжно

1. Скопируйте `probe_light_features.py` или `probe_cover_features.py`,
   поменяйте `device_type` и диапазон `feature`.
2. Запустите — создаст пробные устройства с короткими именами.
3. Откройте веб-морду Akubela (`https://<IP>/menu/apicontrol` →
   Устройства → редактировать) — там в поле "Выберите функцию" видна
   **человекочитаемая подпись** для каждого `feature`, это надёжнее
   визуального осмотра виджета на экране панели.
4. Впишите найденный номер в `device_registry.py`, удалите пробники
   (`--cleanup`).

## Как добавить новый тип устройства (домен)

Пример: хотим поддержать `media_player`.

1. **`device_registry.py`**:
   - Добавить в `AKUBELA_DOMAIN_BY_DEVICE_TYPE` соответствие
     `device_type` Akubela → HA-style домен на стороне панели (нужно
     для случаев типа `input_boolean` → `switch`, когда домены не
     совпадают).
   - В `build_device_spec()` добавить `if domain == "media_player": return {...}`
     с подходящим `device_type` (см. Appendix 2 официального
     OpenAPI-документа Akubela — там полный список `product_type`/
     `device_type`).
   - Если у нового домена свои сервисы (не `turn_on`/`turn_off`) —
     добавить ветку в `resolve_state_service()`.

2. **`config.py`**: добавить домен в дефолт `PUSH_DOMAINS` (или просто
   прописать в `.env`).

3. **`state_forwarder.py` / `control_bridge.py`**: если нужно
   пробрасывать не только "включено/выключено", а специфичные
   атрибуты (как `brightness`/`color_temp` для света, `temperature`
   для climate) — добавить отдельный блок по образцу существующих, с
   собственным словарём для дедупа (`self._last_sent_XXX`).

4. Прогнать `test_connect.py` → `test_roundtrip.py`, проверить, что
   устройство появилось на панели и управление работает в обе стороны.

## Ручная правка виджета через веб-морду Akubela

Если автовыбор `feature` не подошёл (виджет не тот, что нужен) — можно
**вручную** поменять его прямо в веб-морде Akubela
(`https://<IP_панели>/menu/apicontrol` → Устройства → редактировать).

С определённого момента `sync_service.py` **не трогает** уже
созданные устройства — при следующей синхронизации он просто примет
то, что реально стоит на панели, как источник правды, и обновит
`bridge_state.json` под это. Ручная правка не будет откачена обратно.

Ограничение веб-формы: имя длиннее ~32 символов и не тот формат ID
устройства вызывают ошибку при сохранении — бридж сам обрезает имена
до 32 символов при создании, чтобы потом можно было спокойно
редактировать через веб-морду.

Если наоборот нужно **откатить** ручную правку и вернуть то, что
выдал бы код (например, после того как поправили маппинг в
`device_registry.py`):
```bash
python force_resync.py --list                     # посмотреть все entity_id
python force_resync.py light.some_entity_id        # удалить с панели + из store,
                                                     # пересоздастся с дефолтом кода
                                                     # при следующем full_sync
```

## Что делать, если виджет "не подходит"

Каждому `device_type` в Akubela соответствует несколько `feature`
(0, 1, 2, 3...) — разные варианты виджета с разным набором элементов
управления (просто выключатель / диммер / диммер+цвет / RGB и т.д.).
Соответствие `feature` → набор возможностей **не задокументировано** и
не следует напрямую из `device_config` — единственный надёжный способ
узнать — визуально посмотреть на панели.

### Процедура калибровки (на примере уже сделанного для `Light`)

1. Используйте `probe_light_features.py` как образец (или скопируйте
   и адаптируйте под другой `device_type` — конструкция та же:
   `device_add()` в цикле по возможным `feature` с понятными именами).
   ```bash
   python probe_light_features.py            # создаст Feature 0..15
   ```
2. Откройте панель, по очереди посмотрите на каждый созданный виджет,
   найдите тот, у которого есть нужный набор элементов управления.
3. Запишите номер `feature` — обновите соответствующую константу в
   `device_registry.py` (например `LIGHT_FEATURE_COLOR_TEMP`).
4. Уберите тестовые виджеты:
   ```bash
   python probe_light_features.py --cleanup
   ```
5. `python test_connect.py` — устройство, у которого поменялся
   `feature`, будет автоматически пересоздано с новой конфигурацией
   (сравнение "изменилась ли конфигурация" в `sync_service.py` само
   определит несоответствие).

### Если device_config тоже нужно подобрать

Некоторые `feature` требуют дополнительных полей в `device_config`
(например `color_temp_min`/`color_temp_max` для света). Смотрите
Appendix официального OpenAPI-документа Akubela — там есть примеры
`device_config` под каждый тип абилки (ability). Если и там нет —
пробуйте с разумными дефолтами (как в `probe_light_features.py`,
`_CT` для всех нечётных на всякий случай) и проверяйте по факту.

## Как исключить сущность из синхронизации

В `.env`:
```
EXCLUDE_ENTITIES=sensor.something_not_needed,light.test_lamp
```
При следующем `full_sync` она не только перестанет пушиться, но и
будет **удалена** с панели, если уже была там зарегистрирована
(`_prune_out_of_scope()` в `sync_service.py`).

## Как найти и убрать "осиротевшие" устройства на панели

Устройства, созданные вручную/старыми экспериментами и не привязанные
к текущему бриджу:
```bash
python cleanup_orphans.py            # только посмотреть (dry-run)
python cleanup_orphans.py --delete   # удалить после подтверждения
```

Это чистит только **сторону Akubela**. Если проблема в обратную
сторону — в HA висят "сущности-призраки" от родных устройств
(`native_switch_bridge.py`/`native_lock_bridge.py`), чей источник на
Akubela уже удалён, но retained MQTT-конфиг остался — используйте
отдельный инструмент:
```bash
python cleanup_mqtt_ghosts.py            # только посмотреть (dry-run)
python cleanup_mqtt_ghosts.py --delete   # удалить осиротевшие MQTT-конфиги
```
**Важно:** перед запуском остановите `main.py` — иначе он будет
одновременно переподписываться на те же топики и мешать сбору.

## Чтение логов: что означают предупреждения

- `удалил устройство вне области видимости: ...` — нормально, сработала
  подчистка (`_prune_out_of_scope`), не ошибка. **Важно**: если вы
  видите это про свои же родные устройства (реле, домофон) после
  обновления кода — это самоисправление реального бага (см.
  `ARCHITECTURE.md`, "родные switch/lock дублировали сами себя"), не
  повод для тревоги.
- Устройство уже существует на панели — `sync_service.py` больше **не
  пересоздаёт** его автоматически при рассинхроне `device_type`/
  `feature` (панель — источник правды, см. `ARCHITECTURE.md` раздел 15).
  Если нужно намеренно пересоздать — `force_resync.py <entity_id>`.
- `id_ext_next() пуст, использую хэш ...` — панель не отдала свой ID,
  сработал автоматический откат, не ошибка (см. `test_id_ext.py`).
- `не обрабатываю state=... для ... (domain)` — для этого состояния
  нет сервиса в `resolve_state_service()` (например переходное
  `opening`/`closing` у `cover` — так и задумано, не форсим).
- `позиция (подтверждение) -> 100/0` — после `open_cover`/`close_cover`
  бридж досылает явную позицию как подтверждение конечной точки (у
  виртуальной шторы нет концевика, панель иначе может не понять, что
  движение завершилось), не ошибка.
- `отложенный досыл (rate limit истёк): ... -> ...` (от
  `rate_limited_sender.py`) — нормально: значение попало в окно
  rate-limit, было отложено и теперь досылается актуальным. Раньше
  такие значения терялись насовсем (нужно было вводить их повторно) -
  теперь досылаются автоматически.
- `похоже на бесконечную петлю (...) - ПРИОСТАНАВЛИВАЮ пересылку` —
  `loop_guard.py` обнаружил дребезг. Ищите причину: сторонняя
  автоматизация на HA/панели, реагирующая на любое изменение состояния
  переключением. Пересылка для этой сущности возобновится сама через
  `suspend_sec` (по умолчанию 60с), либо перезапустите процесс.
- `[RAW] ...` (в `scene_control_bridge.py`) — диагностический вывод
  сырых событий для калибровки активации сцен, не ошибка.
- `%s: пропускаю (rate limit, ...)` / `значение не изменилось` —
  нормальная работа антипетлевой защиты для света и позиции `cover`,
  не ошибка.
